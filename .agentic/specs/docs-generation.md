# Documentation Generation Spec

**Status: DRAFT**

## Summary

Set up dual-format documentation generation for the agentrack library. Two formats are produced from the same source code JSDoc comments: HTML documentation for users (published via GitHub Pages) and Markdown documentation for AI agents (readable directly from the repo). Both are generated to the `docs/` directory at the repository root as part of the release workflow, owned by the library-release agent.

## Motivation

agentrack is a library — documentation is a first-class deliverable alongside the code. Two audiences need different formats:

1. **Users** (humans) — browse HTML docs on GitHub Pages with navigation, search, and rich formatting
2. **AI agents** — read concise Markdown directly from the repo to understand the API without rendering HTML

Both formats must be generated from the same JSDoc source to stay in sync automatically.

## Requirements

### R1: HTML documentation for users
- Generated by TypeDoc with the default HTML theme
- Output to `docs/html/` at the repository root
- Includes all public API: Tracker class methods, types, error codes
- Published to GitHub Pages via the existing release workflow

### R2: Markdown documentation for agents
- Generated by TypeDoc with typedoc-plugin-markdown
- Output to `docs/md/` at the repository root
- Concise format optimized for agent consumption: no breadcrumbs, no page headers, flat structure
- Includes the same content as HTML (all public API)

### R3: npm scripts
- `docs:html` — generates HTML documentation only
- `docs:md` — generates Markdown documentation only
- `docs` — generates both formats
- `docs:check` — validates documentation completeness without writing files

### R4: Gitignore
- `docs/` directory added to root `.gitignore` (generated artifacts are not committed)

### R5: Release integration
- Documentation generation is a mandatory step in the release workflow
- library-release agent generates/verifies docs before every release
- GitHub Actions release workflow updated to deploy HTML docs from the new `docs/html/` location

## Configuration Guidance

### typedoc.json (packages/library/typedoc.json)
Remove the `out` field from the config — output paths will be specified per invocation via CLI flags. Keep all other settings (entryPoints, readme, exclude*, categorizeByGroup, categoryOrder).

### npm scripts (packages/library/package.json)
Replace the current `docs` script. The implementer should determine exact CLI flags for typedoc-plugin-markdown options (hideBreadcrumbs, hidePageHeader, etc.) based on the plugin's documentation. Output paths are relative to `packages/library/`:
- HTML: `--out ../../docs/html`
- Markdown: `--out ../../docs/md` with `--theme markdown` plus conciseness flags

### typedoc-plugin-markdown
Keep the existing devDependency — it is now needed for markdown output. Issue mp3pe9lvdq (cleanup) should be closed.

### Release workflow (.github/workflows/release.yml)
Update the docs deployment step to use `docs/html/` at repo root instead of `packages/library/docs-html/`.

## Pre-requisites (CTO tasks)

1. Update `.claude/agents/library-release.md` access rules to include `docs/**` (so the agent can write generated docs to the repo root)
2. Update root `.gitignore` to include `docs/`
3. Close issue mp3pe9lvdq (typedoc-plugin-markdown cleanup — plugin is now needed)

## Out of Scope

- Custom CSS/theming for HTML docs (default TypeDoc theme is fine)
- Search functionality in HTML docs (TypeDoc default)
- Additional documentation beyond what TypeDoc generates from JSDoc
- Version-specific or versioned documentation
- Publishing to GitHub Pages (already handled by release workflow, just path update)
- Tutorial content or getting-started guides (README covers this)

## Acceptance Criteria

1. `bun run docs:html` generates complete HTML API documentation to `docs/html/` at repo root
2. `bun run docs:md` generates complete Markdown API documentation to `docs/md/` at repo root
3. `bun run docs` generates both formats in sequence
4. `bun run docs:check` validates documentation without generating files
5. Both formats include all public API: Tracker class methods, types, error codes
6. Markdown output is concise — no navigation chrome, no breadcrumbs, flat file structure
7. `docs/` is in root `.gitignore`
8. `bun run quality` still passes after changes
9. Old `docs-html/` directory inside `packages/library/` is cleaned up
10. GitHub Actions release workflow deploys from `docs/html/`
